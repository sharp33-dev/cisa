영역 2 · 정답 해설 / 오답 분석 / 이론
정답 해설

전통적 MVC는 여러 GoF 패턴의 조합으로 설명된다.
- Observer: 모델의 상태 변화가 뷰에 통지되어 갱신되는 구조(모델-뷰 관계)
- Strategy: 뷰가 컨트롤러를 교체 가능한 전략처럼 사용(입력 처리 정책 교체)
- Composite: 뷰가 하위 뷰(위젯)들을 트리로 구성하는 계층 구조

Chain of Responsibility(책임 연쇄) 는 요청을 처리 객체들의 사슬을 따라 전달하는 패턴으로, MVC의 핵심 상호작용을 설명하는 표준 패턴 조합에는 포함되지 않는다. 따라서 가장 적절하지 않은 것은 ④번이다.

오답 분석

보기①

Strategy는 뷰-컨트롤러 관계(입력 처리 전략 교체)로 MVC에서 사용된다.

보기②

Observer는 모델→뷰 상태 통지의 핵심 패턴이다.

보기③

Composite는 뷰의 계층적 구성(위젯 트리)에 사용된다.

관련 이론 정리
  • MVC ≒ Observer + Strategy + Composite 조합으로 자주 설명된다.

  • Chain of Responsibility: 이벤트 핸들링 파이프라인 등에 쓰이나 MVC 3요소 상호작용의 정의 패턴은 아니다.

  • 시험 포인트: "MVC 구성 패턴 3종(Observer·Strategy·Composite)"을 기억하고 나머지를 고른다.

정답 해설

코드에서 RealSubject와 Proxy는 Subject 인터페이스를 implements(구현) 한다. UML에서 인터페이스 구현(실현, Realization)은 점선 + 속이 빈 삼각형 화살표로 표기한다. 또한 Proxy는 private RealSubject 필드를 보유(-realSubject) 하므로 Proxy→RealSubject는 연관(Association) 이며 실선 화살표로 표기한다.

따라서 두 implements를 점선 삼각형(실현)으로, Proxy→RealSubject를 실선 연관(-realSubject)으로 표현한 ③이 가장 적절하다. 실현을 실선으로 그리거나(①) 연관을 점선으로 그린(②④) 것은 UML 표기 규칙에 어긋난다.

보기①

implements(실현)를 실선 삼각형으로 표기 → 실현은 점선이어야 하므로 오답(실선 삼각형은 상속/일반화).

보기②

Proxy→RealSubject 연관(필드 보유)을 점선으로 표기 → 연관은 실선이어야 한다.

보기④

연관을 점선(의존)으로 표기 → 필드 보유는 의존이 아니라 연관(실선)이다.

어떤 시스템의 MTBF(Mean Time Between Failures) = 5시간, MTTR(Mean Time To Repair) = 2시간일 때, 해당 시스템의 가용성은?

보기

① 0.2
② 0.4
③ 0.6
④ 0.8

정답

정답 : ③번

정답 신뢰도 : 매우 높음 (원본 이미지 Bold 확인)

핵심 키워드
  • 가용성 = MTTF / (MTTF + MTTR)
  • MTBF = MTTF + MTTR
문제 정보
항목 내용
연도 2026년 (제27회)
과목 소프트웨어공학
문항번호 30번
난이도 중
출제주제 가용성(Availability) 계산 - MTBF/MTTR
영역 2 · 정답 해설 / 오답 분석 / 이론
정답 해설

가용성(Availability)은 전체 시간 중 정상 가동 시간의 비율로, A = MTTF / (MTTF + MTTR) 로 정의된다. 여기서 MTBF = MTTF + MTTR(고장 간 평균시간 = 평균 가동시간 + 평균 수리시간)이다.

  • MTBF = 5, MTTR = 2 → MTTF = MTBF − MTTR = 3
  • A = MTTF / MTBF = 3 / 5 = 0.6

따라서 정답은 ③ 0.6이다.

※ MTBF를 "가동시간"으로 오해해 5/(5+2)=0.71로 계산하면 함정이다. 표준 정의상 MTBF는 MTTF와 MTTR을 포함한다.

오답 분석

보기①·②·④

0.2, 0.4, 0.8은 MTTF(3)와 MTBF(5)의 비(0.6)에서 벗어난 값이다. 특히 0.8은 MTTF를 4로 오산하거나 다른 조합으로 계산한 오답이다.

관련 이론 정리
  • A = MTTF/(MTTF+MTTR) = MTTF/MTBF

  • 가동률↑: MTTF(신뢰성)↑, MTTR(정비성)↓

  • 시험 포인트: MTBF·MTTF·MTTR의 관계(MTBF=MTTF+MTTR)를 정확히 적용.

출제주제 시퀀스 다이어그램 - break 조합 프래그먼트 실행 흐름
영역 2 · 정답 해설 / 오답 분석 / 이론
정답 해설

UML 상호작용의 break 프래그먼트는 "조건이 참이면 break 내부를 실행하고 그것을 감싼 상위 프래그먼트의 나머지 흐름을 중단(탈출)"하는 의미를 가진다. 조건이 거짓이면 break 내부를 건너뛰고 나머지를 정상 진행한다.

적법한 하나의 실행 흐름(trace) 예로 ② a → d → f 가 성립한다: a 수행 후, 첫 break(z>3)의 조건이 거짓이어서 b·c를 건너뛰고 d를 수행, 이어 두 번째 break(w==2)의 조건이 참이 되어 f(브레이크 내부)를 수행하고 종료하는 흐름이다. 따라서 정답은 ②이다.

④(a→b→c→d→e→f)처럼 break 내부와 이후 흐름이 모두 실행되는 것은 break 의미(탈출)에 어긋나며, ①·③도 프래그먼트 구조상 성립하지 않는 조합이다.

오답 분석

보기①

a 이후 곧바로 f로 가려면 중간 프래그먼트 구조를 건너뛰어야 하는데, 이는 제시된 프래그먼트 경계와 맞지 않는다.

보기③·④

break 조건이 참이면 내부 실행 후 상위 흐름을 탈출해야 하므로, break 내부(b,c 또는 e,f)와 이후 메시지가 모두 순차 실행되는 조합은 성립하지 않는다.

관련 이론 정리

주요 결합 프래그먼트: alt(택1), opt(선택), loop(반복), par(병행), break(조건 시 탈출), seq/strict(순서).

  • 시험 포인트: break = "실행 후 상위 프래그먼트 탈출"이라는 의미를 흐름 추적에 적용.

  • 시험 포인트: entry/exit의 실행 순서와 복합상태 진입·이탈 순서를 정확히 적용해야 한다.

LSP(리스코프 치환 원칙) 는 "자식 타입은 부모 타입을 대체(치환)해도 프로그램의 정확성이 유지되어야 한다"는 원칙으로, 일반화(상속) 관계의 적절성을 점검하는 데 쓰인다. 그러나 LSP 위반은 의미론적·행위적 계약 위반이어서 컴파일러가 자동으로 에러를 발생시키지 못한다(런타임 오류나 논리적 결함으로 나타남). 따라서 "위반하면 컴파일러가 자동으로 에러를 발생"이라고 한 ④가 가장 거리가 멀다.

①(SRP: 단일 변경 이유), ②(OCP: 확장에는 열려·변경에는 닫힘), ③(DIP: 변화가 적은 추상에 의존)은 모두 옳다.

보기①

보기②

OCP는 기존 코드 수정 없이 확장으로 기능 추가가 가능해야 한다는 원칙으로 옳다.

보기③

DIP는 구체(자주 변함)가 아니라 추상(변화가 적음)에 의존하라는 원칙으로 옳다.

LSP 자식은 부모를 치환 가능

DIP 추상에 의존

문제

마이크로서비스 설계를 위한 그림(각 서비스가 자체 Database 보유, Message Broker·Orchestrator)의 특정 패턴을 적용하기 위한 Best Practice로 가장 적절한 것은?

보기

① 데이터베이스는 비즈니스 규칙이 아닌 데이터를 저장하기 위한 용도로만 사용되어야 한다.
② 데이터를 읽고, 쓰는 책임을 분리하는 CQRS 코딩 패턴을 적용해야 한다.
③ 서비스간 통신오류 방지를 위해 연관 ID를 정의하여 사용해야 한다.
④ 비동기 메시지의 구조를 잘 이해하고 정의해야 한다.

영역 2 · 정답 해설 / 오답 분석 / 이론
정답 해설

그림은 각 서비스가 자체 데이터베이스를 소유(Database per Service) 하고 Message Broker로 비동기 통신하는 전형적 MSA 구조이다. 이때 서비스별로 분산된 데이터를 효율적으로 조회·갱신하기 위한 대표 Best Practice가 CQRS(명령/조회 책임 분리) 로, 읽기(Query) 모델과 쓰기(Command) 모델을 분리하여 확장성과 성능을 높인다. 따라서 가장 적절한 것은 ②이다.

③(상관관계 ID로 분산 추적)과 ④(비동기 메시지 구조 이해)도 MSA에서 유용한 실천이지만, 그림이 강조하는 "서비스별 DB + 읽기/쓰기 분리"라는 특정 패턴 적용의 Best Practice로는 CQRS가 가장 적절하다.

오답 분석

보기①

"DB는 데이터 저장 용도로만"은 일반 원칙일 뿐, 그림의 특정 패턴(서비스별 DB) 적용 Best Practice로는 초점이 아니다.

보기③

상관관계 ID(Correlation ID)는 분산 추적·로깅에 유용하나 "통신오류 방지" 목적으로 한정 서술되어 그림의 핵심 패턴과 정확히 부합하지 않는다.

보기④

비동기 메시지 구조 이해는 필요 조건이나, 특정 패턴(읽기/쓰기 분리) 적용의 Best Practice를 직접 지목하지 못한다.

관련 이론 정리
  • Database per Service: 서비스별 독립 DB → 결합도↓, 그러나 분산 데이터 일관성(Saga) 필요.

  • CQRS: 명령(쓰기)과 조회(읽기) 모델 분리, 이벤트 소싱과 자주 결합.

  • 시험 포인트: "서비스별 DB + 읽기/쓰기 분리 = CQRS".

영역 2 · 정답 해설 / 오답 분석 / 이론
정답 해설

전방계산(ES/EF)
- T1: 0~4
- T2: 4~11, T3: 4~13
- T4: 11~17, T5: max(11,13)=13~24
- T6: 13~21
- T7: max(17,24)=24~34
- T8: max(21,34)=34~40 → 프로젝트 완료 40일

후방계산(LS/LF) (완료 40 고정)
- T8: 34~40
- T7: 24~34, T6: LF=34 → LS=34−8=26
- T5: 13~24, T4: 18~24
- T3: 후속 T5(LS13)·T6(LS26) → LF=13, LS=4
- T2, T1 …

T6의 Slack = LS − ES = 26 − 13 = 13일 → 정답 ③.

즉 T6는 최대 13일까지 늦어져도 전체 일정(40일)에 영향을 주지 않는다(주경로는 T1-T3-T5-T7-T8).

오답 분석

보기①②④

8·11·15일은 ES/LS 계산 착오(예: T6 후속 T8의 LS를 잘못 산정)로 나오는 값이며, 정확한 후방계산에서 T6 Slack은 13일이다.

관련 이론 정리
  • 주경로(여유 0): T1→T3→T5→T7→T8 (4+9+11+10+6 = 40).

  • Slack(Total Float) = 각 활동의 LS−ES. 주경로 활동의 Slack은 0.

  • 시험 포인트: 후방계산에서 후속 활동의 LS 최솟값으로 LF를 정하는 것이 핵심.
